Privacy Policy

Effective 2026-09-12

gcal-sync is open-source software that you download and run yourself, on infrastructure you control. The project maintainer does not operate a hosted version of this service and never receives, stores, or has access to your Google account data. This policy describes how the software itself handles data when you run your own instance of it.

If you're using someone else's deployment of this software rather than running your own, that deployment is a separate operator's instance — see its own privacy policy (typically at its /privacy path) for how that specific operator handles your data.

Google data this software accesses

gcal-sync requests two narrow Google Calendar API scopes and nothing else:

  • calendar.events — to read events on the calendars you configure, and to create, update, or delete the private “Busy” placeholder events it uses to mirror availability across them.
  • calendar.calendarlist.readonly — to list the calendars visible to an authorized account, so you can pick which calendar ID to sync (used only by the calendars command).

gcal-sync never requests access to Gmail, Drive, Contacts, or any other Google product.

What gets copied between calendars

The Calendar API returns full event data (including title, description, attendees, location, and conferencing links) when gcal-sync reads your calendar. By default, only the start/end time, busy/free status, and recurrence pattern are copied into a placeholder mirror event on the other calendars. Events marked “Free” are ignored entirely.

You can explicitly opt a specific direction between two of your own calendars into “full copy” mode (via the FULL_COPY_PAIRS configuration setting), which additionally mirrors the event's title, description, location, and meeting link. This is off by default for every calendar and must be turned on deliberately per direction. Attendees are never copied, under either mode.

For any calendar direction where full copy is not enabled, titles, descriptions, attendees, locations, and conferencing links exist only in memory for the moment it takes to process each event during a sync pass, and are discarded immediately afterward — they are never written to disk, to the local database, to logs, or anywhere else.

Where data is stored

Everything gcal-sync needs to operate — OAuth tokens and a record of which source events map to which mirror events — is stored locally on the machine you deploy it on (as local files and a local SQLite database). None of it is transmitted to the project maintainer, to analytics providers, or to any other third party.

How this data is protected

All requests to Google's Calendar API are made over HTTPS/TLS; gcal-sync never transmits OAuth tokens or calendar data over an unencrypted connection.

OAuth tokens are written to local files with permissions restricted to the operating system user running gcal-sync (mode 0600: readable and writable only by that user). No other process or account on the machine can read them without elevated privileges, and nothing is transmitted off the machine except the HTTPS calls to Google's Calendar API described above.

If you're using a hosted deployment operated by someone else rather than running your own instance, that operator's own privacy policy (typically at its /privacy path) describes the additional protections — such as encryption at rest — it applies to data stored on its infrastructure.

Data sharing

gcal-sync makes outbound HTTPS requests only to Google's Calendar API. It does not include analytics, tracking, advertising, or any other third-party integration.

Data retention and deletion

Data is retained only for as long as you, the operator, keep it. Deleting the local data/ directory removes all stored tokens and sync state. You can revoke gcal-sync's access to your Google account at any time from Google Account → Security → Third-party access.
